📝 תקציר מנהלים

מטרת הפרויקט היא בניית ממשק גרפי מודרני (GUI) למערכת ה-Python Core הקיימת, תוך שמירה על הלוגיקה העסקית הקיימת ושיפור חוויית המשתמש. הארכיטקטורה הנבחרת מבוססת על React + Vite בחזית, FastAPI כשכבת גישור (BFF), ו-RabbitMQ לתקשורת א-סינכרונית, עם עדכוני זמן אמת באמצעות SSE.

2. הצדקת בחירות טכנולוגיות (ADR)

🐍 למה FastAPI וללא Django או Node.js?

הסיבה: התאמה מושלמת ל-Python Core הקיים.

  • שיתוף קוד: ניתן לשתף מודלים (Pydantic), סוגים (Type Hints) ולוגיקת אימות ללא התאמות.
  • ביצועים: תמיכה מובנית ב-async/await לטיפול באלפי חיבורי SSE במקביל.
  • פשטות: קל יותר להטמעה מ-Django (כבד מדי ל-BFF טהור) ויעיל יותר מ-Flask.
  • לא Node.js: אינו דורש כפילות של לוגיקה בשפות שונות. המערכת היא Python, ולכן Python BFF היא האופציה היעילה ביותר.

📊 האם יש מסד נתונים ב-BFF?

התשובה: לא. ה-BFF יישאר Stateless לחלוטין.

ההסבר: תפקיד ה-BFF הוא רק תרגום והפצה. כל הנתונים נשמרים ב-Core או במאגרים ייעודיים אחרים. שמירת נתונים ב-BFF תיצור צומת כשל יחיד ותיקשה על Scaling.

⚡ למה SSE ולא WebSocket?

ההשוואה:

היבטפתרון נבחר (SSE)אלטרנטיבה (WebSocket)
כיווןחד-סטרי (שרת → לקוח) + REST לפקודותדו-סטרי מלא
פשטותHTTP סטנדרטי, קל ל-Debug ו-Proxyפרוטוקול מיוחד, מורכב יותר לניהול
חסימותפועל על כל ה-Firewalls/Proxiesעלול להיות חסום ב-Proxies ישנים

מסקנה: מכיוון שאנחנו צריכים בעיקר עדכוני סטטוס לרוב, SSE הוא פתרון מינימליסטי, יציב וקל יותר לניטור.

3. איתנות וטיפול בכשלים (Resilience)

3.1 מה קורה אם התקשורת נופלת?

  • Reconnect אוטומטי: המנגנון ב-SSE מחדש את החיבור אוטומטית כשהקו מתנתק, ומאחזר את האירועים שנפספסו באמצעות Last-Event-ID.
  • Fallback ידני: אם החיבור נכשל לאורך זמן (>30 שניות), הממשק יציג התראה "ניתוק חיבור" עם כפתור "רענון" ידני.
  • ללא Polling מיותר: לא נבצע Polling רציף כדי לא להעמיס על השרת, אלא רק במקרה של כשל מתמשך.

3.2 איך מתמודדים עם עומס אירועים?

אם ה-Core שולח אלפי אירועים בשנייה, ה-UI עלול לקרוס.

  • Debounce ב-Client: עדכוני UI יתארגנו כל 100-200ms (לא כל אירוע ירנדר מיד).
  • Throttling ב-BFF: FastAPI יגביל את קצב השידור ל-Max 50 events/second למשתמש.
  • עיבוד בולות: RabbitMQ יאפשר הפרדה בין Events קריטיים (אזהרות) ל-Events רגילים (לוגים), כך שראשית תתעדן על החשוב.

4. רכיבי צפי עתידי (Open Questions)

  • אימות (Authentication): עדיין לא מוגדר. מומלץ OAuth2 / JWT בשלב 2.
  • מטמון (Caching): ניתן להוסיף Redis לנתונים נגישים מאוד אם יידרש.
  • לוגים ו-Audit: האם לשמור את כל הלוגים במאגר מיוחד (ELK) או רק להציג אותם בזמן אמת?

5. סיכום

הארכיטקטורה הנבחרת היא פתרון מינימליסטי, יציב וקל לטיפול: React + FastAPI + RabbitMQ + SSE. היא מנצלת את יתרונות ה-Python הקיים, מונעת כפילות, ומספקת חוויית משתמש חיה ויציבה תוך התמודדות עם כשלים ותרגול.
